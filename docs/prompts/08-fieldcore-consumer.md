# 08 — Prove the FieldCore-node consumer contract

## Inputs

Apply [COMMON](COMMON.md). Consume `owner-contract` with `value-status`, `rtu-codec`, `measurements`, `configuration` and `device-health`. This stage produces `consumer-fixture`. Read [CONVENTIONS](CONVENTIONS.md) and the pinned FieldCore-node headers, SHZK caller, VibWire caller and owner fake in the [source map](SOURCE_MAP.md). Inspect the listed `main` and `rodtester` revisions separately.

## Work

1. Build a small native consumer fixture in SEN059x using the installed-style public include `<SEN059x/SEN059x.h>` and the stage 07 owner tests. Follow `ShzkDeviceModule` for constructing the request directly into the owner's transaction storage and parsing borrowed RX bytes. Follow `VibWireDeviceModule` for yielding a wait between steps. Keep the fixture's bounded consumer types in test/example code. A clean SEN059x checkout must run it offline without a FieldCore checkout or its private headers.
2. Exercise the sensor subset of `Rs485DeviceBinding` through `bind`, `applyRuntimeConfig`, `start`, `poll`, `takeStep`, `acceptObservation`, `takeResult`, `cancel`, `setEnabled`, `onBusInvalidated` and cached `snapshot`, `readingCatalog`, `copyStatus`. A step yields `Rs485ModuleAction::None`, `RequestTransaction` or `WaitUntil`. Preserve the declared `DeviceCommand` identity (`requestId`, `deviceId`, `kind`, `deadline`) through exactly one terminal result for each accepted command. Hold that result until taken. Unsupported, expired, disabled or busy admissions must leave pending work intact.
3. Implement `DeviceRequestKind::Probe`, `Measure` and `ReadLast` in the fixture. Probe via an addressed, non-ranging read such as baud register `0x0201`. A valid response proves a responsive endpoint. The SKU remains the configured one. Probe has no measurement payload. Measure requests one selected register with the public builder/parser and decodes against that SKU. Associate each result with its own reading ID/unit, returned raw word, validity and sample time. Individually triggered registers have independent acquisition times. ReadLast uses the existing cache/freshness rules and preserves the acquisition timestamp with zero bus I/O.
4. Retain `DeviceModuleStartStatus` (`Accepted`, `Busy`, `Disabled`, `Unsupported`, `Rejected`), `DeviceModulePollState` (`Idle`, `Running`, `Complete`, `NeedsBusRecovery`) and `DeviceResultStatus` (`Ok`, `Disabled`, `Absent`, `Timeout`, `Stale`, `Cancelled`, `Failed`) in the consumer mapping. Explain which paths apply to this sensor. Copy `completedUptimeMs`, `readingCount`, `validMask`, `staleMask` and `errorMask` consistently. Administrative cancellation conserves a request and preserves the last operational result and last successful reading.
5. Use the real SHZK error translation. Map `FRAME_TOO_SHORT` to `Rs485ParserError::TruncatedFrame`, `CRC_MISMATCH` to `BadCrc`, wrong address/function to `UnexpectedAddress`/`UnexpectedFunction`, and byte-count or length mismatches to `ValueCountMismatch`. Use `ExceptionResponse` and preserve the raw Modbus exception in the backend detail. Keep `None` for success, `UnsupportedFrame` for an otherwise unmapped protocol failure and `OutOfRangeValue` for a positively established semantic range failure. An uncertain documented reading retains raw data and its specific measurement disposition. A valid attributable exception counts once as successful communication for the stage 06 observer and as an exception for the attempt. If terminal, the operation fails. The sample stays unchanged.
6. From the owner observations project `DeviceModuleStatus` with separate `HealthState` (`Initializing`, `Ok`, `Degraded`, `Fault`, `Unknown`, `Disabled`) and `PresenceState` (`Unknown`, `Present`, `Absent`, `Disabled`). Use the existing lower-case display literals. Specify configured stale/fault miss thresholds and recovery on a subsequent success. Count verified no-byte misses separately from corrupt replies, foreign replies and valid device exceptions. Track `lastAttemptUptimeMs`, `lastSuccessUptimeMs`, `lastErrorUptimeMs` and success/error/timeout counts. Check `Rs485DeviceStatus` fields `lastStatus`, `lastParserError`, `parserErrorCount`, `consecutiveMissCount`, `staleCount` and `validMask`. Feed the corresponding device observations to the library's passive `DeviceHealth` and inspect its `HealthSnapshot`. Preserve product enable policy, presence, freshness and bus health as distinct consumer decisions.

## Acceptance

Run a consumer executable against the same public API for both owner revisions. Exercise real differences using a narrow host fixture or separate build modes. Record what each revision can establish.

| Consumer surface | Evidence to exercise |
| --- | --- |
| FieldCore `main` | `takeStep(step)`, 8-byte TX and 192-byte RX, `FixedLength`/`Suffix`, request-echo stripping. The default fixed-length collector can finish on a prefix and cannot prove frame closure or distinguish FC06 ACK from local echo. Show supported calls and an inconclusive result for missing evidence. Never manufacture a qualified RTU observation from these fields. |
| FieldCore `rodtester` | `takeStep(step, nowMs)`, 21-byte TX and 192-byte RX, `Rtu` with `QualifiedResponse` or `Ambiguous`. Correlate copied step identity/generation. Exercise prefix vs total length, wire errors, qualified closure bounds, actual TX drain and uncertain execution. Give the fake a qualified case and an unqualified case. Its Arduino backend's buffered reads cannot timestamp RTU closure. |
| Profile and hardware ownership | The reference build profiles select SHZK-PT v3.0.0 and VibWire-108 v1.2.0. SEN059x has no selected product binding at these pins. The profile supplies UART, pins and DE polarity. The owner's default is 9600, while both sensors ship at 115200 8N1, address 1. Fixture bindings explicitly select address, format and SKU. |
| Baud capability | Both owner validators accept 9600, 19200, 38400, 57600 and 115200 at 8N1. Show pre-TX rejection for 4800, 14400 and 76800 in the FieldCore-shaped path while the portable device profile retains all eight manufacturer codes. |
| Two devices plus lifecycle faults | Interleave two distinct bindings, probe, measure and cache reads, wrong-address and malformed replies, a valid exception, no-byte timeout bursts and recovery. Verify independent masks, counters, health/presence and a healthy peer. A cancelled or superseded result cannot overwrite a later reading. |
| Uncertain terminal and pending result | Inject an ambiguous FC06 echo, a failed drain, cancellation while active, disable/re-enable, and a duplicate completion after bus invalidation. Assert one terminal per accepted command, zero unsolicited writes, no synthetic freshness on recovery and a second `takeResult` returns false. |
