# Package version and supported build profiles

Use these pins for the SEN059x implementation. SHZK-PT supplies the closest implemented Modbus example and native IDF package. FieldCore-node supplies the environment that must consume the portable library. Their Arduino releases differ by one patch. Build the same ESP32-S3 console source against both. The scaffold currently pins Core 6.1.19, the official platform 8.0.0 and the native IDF 5.5.5 image. It leaves the Arduino subpackages to the platform resolver. The Arduino port, its peer build and the final CI matrix apply the explicit profiles below. ## Public package version and build identity

SEN059x currently declares `0.0.0-dev.0` in `library.json`. Preserve this project's version and its existing SemVer generator through implementation. The FieldCore profile selects SHZK-PT `v3.0.0` and VibWire-108 `v1.2.0`. MotorControl-RS has its own `v1.0.0`. Even the SHZK `v3.0.0` tag and its later inspected head with the same manifest version have different build configurations. Record package version **and** revision. A later SEN059x release uses its own compatibility changes and release decision. [Version source](../../library.json) · [Peer version declarations](https://github.com/janhavelka/SHZK-PT/blob/59d76c502a90bef8038ced2b72a2d50df98184e9/include/SHZK_PT/Version.h) · [Tagged SHZK build](https://github.com/janhavelka/SHZK-PT/blob/361c47c0588fe967e9dc5507ce7a3d85a2f0eb6a/platformio.ini) · [MotorControl-RS manifest](https://github.com/janhavelka/MotorControl-RS/blob/08a88ebb422d1a9f8df9c3036faabf82b3a0983e/library.json)

- Keep `<SEN059x/Version.h>` source-compatible. In namespace `SEN059x`, preserve `VERSION_MAJOR`, `VERSION_MINOR`, `VERSION_PATCH`, `VERSION`, `VERSION_CODE`, `VERSION_INT`, `BUILD_DATE`, `BUILD_TIME`, `BUILD_TIMESTAMP`, `GIT_COMMIT`, `GIT_STATUS` and `VERSION_FULL`. Retain the existing `SEN059X_*` build overrides. The numeric formula is `major * 10000 + minor * 100 + patch`. Compare the full SemVer text for prerelease labels.
- Keep `scripts/generate_version.py check` read-only and keep `sync` idempotent. Verify the actual archive's header, `library.json`, native component version and Doxygen project number in the source tree all agree, including the prerelease label. Readiness checks may report a proposed bump. Bumping, tagging and publication occur only for a requested release.
- The Arduino and IDF `version` / `ver` command and machine handshake report library version, application revision/working-tree status, active framework and version, target/board and protocol schema. Capture the actual compiled framework version and compare it with this profile. Source the application identity from its build. Honor `unknown` where an installed archive lacks library Git metadata. Never assign a checkout's parent firmware revision to a separately installed component.
- The [version stage](26-version-provenance.md) tests build provenance in a source checkout, with a tracked local change, in a detached archive and in an unrelated enclosing Git project. Exercise a failed Git status command. If provenance cannot be determined, `GIT_STATUS` is `unknown`. A successful Git status check with no tracked changes yields `clean`. Keep run-specific metadata outside the generated tracked file. [Generated header](../../include/SEN059x/Version.h) · [Generator](../../scripts/generate_version.py) · [CLI contract](CLI_CONTRACT.md)

## Evidence at handoff

Use separate CI jobs or isolated tool environments for the two Core versions. On Windows preserve the managed PlatformIO installation and use a project-local environment when a different Core is required. Record `pio --version`, `pio pkg list -e <environment>` from the owning project, resolved framework/SDK and tool versions, and `idf.py --version` from the native job. Build and link the real app for each required entry. Run the human/runner script or shared dispatcher fixtures to compare the reported version fields and the same capability inventory. Record whether the evidence came from a host fixture, compile/link or running board. A missing or differing required pin is an open build issue until explained and reverified.
