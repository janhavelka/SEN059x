# 12 — Exercise the host runner and fault recovery

## Inputs

Apply [COMMON](COMMON.md). Consume `shared-cli`, `arduino-example` and `idf-example`. Use the exact [CLI contract](CLI_CONTRACT.md) and stage 08 result dispositions. This stage produces `runner-evidence`.

## Work

1. Create a small Python 3 host client for the examples' **console** port. Provide a quick-start, bounded deadline, explicit port and selectable suite. Support stdlib offline fake streams/transcripts and optional pySerial for a live run. Retain the existing independent read-only sensor probe on the direct RTU adapter. Document both connections and keep exactly one master on the sensor bus.
2. Attach with `@1 session <nonce>`, parse the returned build/board/schema and boot identity, then dispatch the same commands as a human. Match anchored `SEN059X ` JSON records by boot, session, request, phase and operation. Stream partial input within the line limits. Accept one terminal result per operation. Report terminal code, detail, disposition, result evidence, freshness and elapsed time. An accepted `cancel` command can return `OK`. The original cancelled operation ends with `ABORTED` and `data.disposition` of `Cancelled`. The runner must check both status and disposition before passing a measurement assertion.
3. Expose read-only suites for help/version, cached status, each of the four measurements and eight configuration words, finite watch, cancellation and recovery. Expose each of the eight named configuration writes in an explicitly selected single-device suite. Require explicit selection of the separate vendor broadcast send-only suite on a live bench. Give each eligible setting an input, typed command, expected raw FC06 word, per-SKU bounds, expected addressed FC03 readback and restoration procedure. Capture TX/RX or owner counts to prove previews are silent and each admission issues one FC06. Mark missing hardware separately from an assertion that actually fails.
4. Simulate timeouts at admission, after acceptance, after TX and during readback. Inject data in chunks, unsolicited human text, stale or malformed records, duplicate IDs, client disconnect, reboot, late responses and output backpressure. Query retained results after reconnection where available. Permit explicit read-only reconciliation with the current binding. Never repeat a trigger or FC06 automatically to reconstruct a lost terminal result.
5. Record machine-consumable results plus a short human summary for CI or the bench. Include commit, dirty flag or unknown, framework, board, SKU, address, link settings, suite, fixture type and what was actually observed. Bind a recording to its device/build identity. Keep transcripts small and free of machine-specific secrets.
6. Use the stage 09 cases as the common runner input for both Arduino profiles and native ESP-IDF. Verify the session uses the requested build identity and address policy. Run the full matrix offline on both SKUs. Exercise all eight baud rates, extended addresses 248–254, both SKU threshold and range limits, both polarity and UART-unit choices, each valid angle/noise level, reserved assignment and broadcast-read rejection. Exercise conditional FC06 acknowledgement followed by verified raw readback, and device exception without a fresh setting. For vendor send-only FC06 check `scope`, destination 255, `verified=false`, no claimed ACK and no automatic readback/retry. Run a separate addressed read using the intended settings. Preserve the two request IDs and the original uncertain effect even when the subsequent read matches.
7. Add a `readregs` diagnostic suite for all three example profiles. Preserve words in register order and record requested span, configured timeout and underlying Modbus exception. Match fake three-word success, count-one raw-only result, malformed word count, valid exception and timeout. Inject hole/wrap, out-of-range count and broadcast cases before admission. Assert the prior typed samples and setting observations remain intact and transfer counts show no split, retry or fallback. A live multi-word probe may initiate ranging and requires an explicit operator-selected diagnostic run. Identify physical block support per unit and measured span.

## Acceptance

Include a previously verified setting and an address/baud in lost-ACK and send-only cases. A subsequent passive query must distinguish the historical value from current trust. Confirm that a rejected write before TX preserves it and that only an addressed readback can establish a new observed value.

Run the host client in CI against records emitted by the application composition's real dispatcher plus fault-injected fake streams. Compare the register matrix for all three firmware build profiles. Each result row names SKU, framework profile, command, key/register, address policy, expected/actual wire transfers, terminal code, evidence scope and assertion outcome. Exercise valid immediate and accepted/done sequences, stale boot/session, wrong command or operation, truncated JSON, duplicate terminal, oversized line, wrong schema, idle timeout and successful next-line recovery. A timeout/cancel preserves last-good data, a static refusal sends zero bytes and a lost ACK results in at most one FC06. Identify build/link proof, host replay and actual live profiles separately. Name any physical rows still pending.

## Delegation and self-audit

Apply the [stage audit](AUDIT.md). Give the reviewer a capture with a stale session, duplicated terminal and reboot after a write. Check the failed operation cannot emit another FC06 and a subsequent independent query is correlated correctly.

## Handoff

Record `runner-evidence` in [PROGRESS](PROGRESS.md) with the runner path, smoke commands for both ports, replay commands, result schema, pass/fail counts and outstanding HIL rows.
