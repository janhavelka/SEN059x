# Stage execution and self-audit

Use this procedure when executing an original stage or a standalone audit checkpoint. The **lead** owns integration, acceptance results, the ledger and Git operations. Declare the selected output and record the base revision before assigning work. An original stage's own review closes its handoff. A suffixed checkpoint opens a separate examination of the implemented range.

## Delegate

1. Spawn a subagent to read the indicated manufacturer or peer source and inspect the real caller. Ask for the exact expected bytes, names, test case or ownership boundary and a source location. For implementation that splits cleanly, give another subagent a disjoint code or test path. Give each the stage, inputs, scope, shared contracts and expected output. When the Arduino and native IDF stages run concurrently, assign their shared code to one owner.
2. Have an independent subagent review the integrated change from the public entry point. Give the reviewer the stage, relevant operation rows, actual diff and failing/positive cases. Ask them to identify missing functionality, wrong framework or API assumptions, silent fallbacks, state corruption and coverage that exercises only a mock. Require a file, symptom, reproduction and severity for each finding. Reviewers report findings to the lead without committing.
3. If the agent runtime has no delegation facility, record that limitation and perform the same implementation and review passes separately. Continue with the work that can be verified. Subagent summaries are leads to check against the source and executed result.

## Fresh range audit

1. Reread **every linked original prompt in full**. Derive an inventory of its requirements, acceptance cases and scope before consulting former findings. For each original, use the ledger to locate the base SHA, completed SHA or relevant commits, affected paths and original checks. Confirm these anchors against Git history. If an anchor is missing, reconstruct it from commits and file history and record the basis and any remaining uncertainty.
2. Inspect the committed changes between the verified endpoints, the implementation as it exists at the current HEAD, and in-scope local changes. Use `git log --oneline <base>..<finish>`, `git diff <base> <finish>`, `git diff --cached`, `git diff` and `git status --short --untracked-files=all` as appropriate. Open relevant untracked files. Branching or interleaved work can require separate commit/path sets for each original. Follow affected callers and tests outside the initially listed paths. Preserve unrelated edits.
3. Dispatch independent subagents **in parallel** with the original prompts, code paths, commit/diff anchors and relevant test commands. Assign one requirements coverage and scope, one implementation correctness and edge cases, and one tests and code simplicity. Combine roles if needed. Require each finding to identify an original obligation, location and reproducible failure or evidence. The lead compares every finding with the actual code and diff, exercises normal entry points and records its disposition.
4. Fix every confirmed in-scope bug, gap or unnecessary complication. Prefer the simplest readable correction that preserves the original public behavior. Rerun affected tests and each original's required verification on the integrated result, including impacted downstream consumers. Repeat review and remediation until all verifiable requirements pass. If a real prerequisite prevents verification, name the affected rows and retain partial/blocked status for that evidence. For hardware, distinguish a missing observation from a confirmed device failure.
5. Record the short audit report in [PROGRESS](PROGRESS.md). Include the original range, inspected revisions, findings, corrections by file, final commands and outcomes and any unverified cases. If independent checks yield no confirmed findings, say so and report what passed. Retain the audit's tested revision. Later changes to covered behavior, tests or evidence reopen the affected checkpoint before a consumer relies on it. Identify the prior result and record the corrective revision and reruns that supersede it.

## Check the integrated result

- Read each acceptance item again against the resulting files. Trace it through a consumer-visible call, command or build. A declaration without a definition, a command registered only in help, a permanent `UNSUPPORTED` for a documented operation, or a test that bypasses dispatch leaves that row open.
- For the stages that own register behavior, use the [operation cases](OPERATIONS.csv). Each row names one public typed selector, FC, address, literal human command and example word valid on both SKUs. The word is the FC03 reply value or FC06 request value. Rows are independent. Reset the simulated device, choose the SKU, bind address 1 and grant the documented maintenance operation before each confirmed write. A manufacturer case identifier points to a published exchange. The other words are synthetic test inputs. [Original frames](../reference/protocol/modbus_vectors.csv)
- Run each applicable case through the real portable entry point, then the shared human and machine dispatchers as they become available. For an addressed write, check the preview causes zero TX, the confirmed command emits the exact FC06, and a separate same-register FC03 establishes the observed value. Exercise both complete example compositions with the same dispatcher and record their builds. Hardware absence can leave only the observation rows open. [Coverage](COVERAGE.md) · [Version targets](VERSIONS.md)
- Select an independent failure that would detect a reversed byte, skipped permission, stale sample, unbounded wait, wrong command mapping, wrong package identity or incorrect build pin as appropriate to this stage. Demonstrate that the check detects it using a negative fixture, deliberately wrong expected input or a temporary local mutation. Restore the intended state and rerun. Expected results must come from the manufacturer vectors, independently reviewed cases or a peer caller, separate from the production lookup used by the operation.
- When auditing writes, start with a known verified value and simulate loss of the reply. Inspect both the operation and the next passive status query. The old value remains historical and the setting is unconfirmed until addressed readback. For address or baud also check endpoint trust.
- The lead reproduces findings, fixes confirmed omissions at the owning layer and reruns the affected checks. Ask the reviewer to check the fix for substantial issues. Review paths changed since the last audit, including agent changes. Any contradictory source claim receives a citation, an explicit software behavior and a named remaining hardware observation.

## Record the handoff

Append a short evidence entry for the stage to [PROGRESS](PROGRESS.md). Include the stage and output, implemented files and public entry points, delegated roles or fallback, commands actually run, target/versions, evidence type, findings and fixes, regression check, gaps and the next eligible stage. Link paths or run IDs for longer evidence. Identify the tested revision in the run or handoff. A documentation entry included in the implementation commit can use the CI run's immutable SHA after the push.

Mark a stage complete when its software requirements run through the normal entry point and all in-scope findings have been resolved and rechecked. Mark remaining obligations `Partial` or `Blocked` with affected operations, SKU and evidence needed. A disabled fixture, a stub or a pass count that silently omits a required case cannot close an operation. Finish all independent work within the requested stage or range. The checker validates the plan's structure. Test execution and review establish implementation progress.
